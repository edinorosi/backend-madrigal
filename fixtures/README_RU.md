# Термостенд: материалы для исследования

Термостенд — модель измерительного устройства. Штатный клиент читает настройки,
меняет их и запрашивает порции температурных измерений. Задача исследователя —
получить проверяемое описание обмена, которое можно применять к другим записям.

## Что доступно

| Материал | Содержание |
| --- | --- |
| `research/01_configuration.pcap` | Изменение настроек, включение и отключение измерений, два последовательных TCP-соединения. |
| `research/02_variations.pcapng` | Другие настройки, отрицательные температуры, метки разной длины, кириллица, разные размеры порций и отклонённые запросы. |
| `research/03_combined_messages.pcap` | Несколько действий в одной отправке клиента и разные способы разбиения потока на пакеты. |
| `additional/04_new_observations.pcapng` | Дополнительный эксперимент с другими значениями и размерами порций. |
| `diagnostics/` | Варианты третьей записи с отдельными условиями захвата и проверки целостности. |
| `action_journal.csv` | Действия, параметры, время и результаты, показанные штатным клиентом, для каждой записи. |
| `dataset_manifest.json` | Состав набора и происхождение данных. |

## Происхождение и ограничения

Прикладные байты получены при настоящем обмене эталонного клиента и симулятора
через TCP-сокеты на localhost. **Ethernet/IP/TCP-пакеты в приложенных файлах
сгенерированы:** сетевые заголовки, разбиение на сегменты и временная шкала
смоделированы. Это воспроизводимые пакетные примеры для прототипирования,
а не пассивный захват с реального устройства.

PCAP и PCAPNG имеют обычный формат файлов захвата, Ethernet и TCP/IPv4.
Основные записи содержат handshake, прикладной обмен и закрытие соединений;
IP-фрагментации нет. Пакетные чексуммы в основных записях вычислены полностью.
PCAPNG содержит один интерфейс с точностью времени в микросекундах.

Для собственных экспериментов организатор располагает рабочим TCP-стендом
и инструкцией настоящего захвата. Этот компактный набор предназначен для
проверки исследовательских функций. Измерения предельной производительности
требуют отдельной нагрузки.

## Контекст устройства

В пакетных примерах клиент имеет адрес `10.77.0.10`, устройство — `10.77.0.20`,
порт устройства — `46123`. Эти адреса относятся к модели пакетного обмена.
Каждый файл в `research/` и `additional/` — отдельный эксперимент после запуска
стенда. Внутри одного эксперимента настройки сохраняются при переподключении
клиента. В первом файле два последовательных соединения используют одинаковые
адреса и порты.

Настройки, видимые в штатном клиенте:

- включены ли измерения;
- период измерений в миллисекундах;
- температурный порог в градусах Цельсия;
- текстовая метка устройства.

Клиент может запросить несколько измерений. Для каждого он показывает время
устройства в миллисекундах, температуру в градусах Цельсия и признак тревоги.
Тревога означает, что температура достигла порога или превысила его.
Симулятор использует логическое время устройства: оно продвигается при
создании очередного измерения. Оно не равно времени наблюдения TCP-пакета.
При отключённых измерениях клиент получает сообщение об отказе.

## Журнал

CSV сохранён в UTF-8 с обычным CSV-экранированием. Поля:

| Поле | Значение |
| --- | --- |
| `capture` | Путь к записи относительно этого каталога. |
| `session` | Метка экспериментального соединения; это метка журнала, не поле протокола. |
| `action_id` | Уникальная метка действия в журнале. |
| `start_utc`, `end_utc` | Окно действия на смоделированной шкале записи, ISO 8601 UTC. |
| `action` | Действие штатного клиента. |
| `parameters` | Параметры действия в удобном читаемом виде. |
| `observed_result` | Результат, показанный клиентом. |

Последние два поля содержат JSON внутри CSV-ячейки. Это журнал эксперимента,
а не промежуточное представление сетевого протокола. Его можно читать вручную
или обрабатывать своим способом. Обязательный сетевой вход приложения остаётся
PCAP/PCAPNG.

`read-config` — чтение настроек; `set-config` — изменение настроек;
`read-values` — получение указанного числа измерений. Действия `probe-*`
фиксируют контрольные отправки неподдерживаемой команды, недопустимого периода
или некорректной текстовой метки. Их наблюдаемый результат — отказ клиента.
Окна нескольких действий могут совпадать, если клиент отправил их вместе.

Диагностические файлы — варианты того же эксперимента, что и
`research/03_combined_messages.pcap`. Для них повторён соответствующий журнал:
он описывает поведение устройства в исходном эксперименте, даже если
повреждённая запись больше не содержит всех байтов результата.

## Диагностические примеры

| Файл | Условие |
| --- | --- |
| `01_retransmission.pcap` | Повтор тех же TCP-байтов с теми же sequence numbers. |
| `02_reordered.pcapng` | Изменение порядка наблюдения сегментов. |
| `03_missing_segment.pcap` | Пропуск сегмента в записи. |
| `04_snaplen_truncated.pcapng` | Усечение пакета при захвате; original length сохранён. |
| `05_conflicting_overlap.pcap` | Два различающихся варианта одного диапазона TCP-байтов. |
| `06_missing_beginning.pcapng` | Запись началась после установления соединения и первых байтов. |
| `07_чексуммы_offload.pcap` | Смоделированные частичные чексуммы исходящих пакетов при локальном захвате. |
| `08_bad_чексуммы.pcapng` | Отдельный пример некорректной чексуммы. |

Конфликтующее перекрытие и неправильная чексуммы внесены намеренно для
диагностики; это не штатное поведение симулятора. Неизвестные байты остаются
неизвестными, даже если журнал содержит наблюдавшийся результат действия.

Команда самостоятельно выбирает способы исследования и представления
интерпретаций. Дополнительная запись позволяет проверить выводы на новых
наблюдениях; диагностические варианты — показать поведение при неполных
и неоднозначных данных.
