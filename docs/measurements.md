# Измерения ресурсов (ТЗ §10, §13 п.6)

Стенд: 12 vCPU, 14 ГиБ RAM, Arch Linux x86-64, `protocol-lab-api`
в профиле `--release`, rustc 1.97.1, пустой стор, localhost.
Дата прогона: 2026-10-16. Память — `VmHWM` процесса сервера из `/proc/PID/status`.

## Контрольная нагрузка

Генератор — `scripts/perf/gen_load.py` (seed фиксирован, прогон воспроизводим).
Профиль повторяет §10: отдельные TCP-соединения по tuple, произвольная
нарезка потока на пакеты, честные чексуммы:

| Параметр | Профиль ТЗ | Факт |
|---|---|---|
| Исходный capture-файл | до 100 МиБ | 97 210 004 Б |
| Пакетов | 250 000 | 251 114 |
| TCP-соединений | 1000 | 1000 |
| App-кадров | 100 000 | 100 000 |

## Время операций (wall-clock, release)

| Операция | Время | Комментарий |
|---|---|---|
| `POST /captures` (импорт 97 МБ) | 2.6 с | разбор + сессии + персист |
| `GET /captures/:id/sessions` (1000) | 0.01 с | |
| `GET /sessions/:id/messages` (~250) | 0.02 с | |
| Полный обход 1000 сессий по HTTP | 16.15 с | ~1000 roundtrip'ов, доминирует HTTP, не сервер |
| Загрузка журнала (6 действий) + `POST /check` по 251 114 сообщениям | 2.96 с | поиск привязок O(A×M), метки времени парсятся заново на каждое действие |

Проверка возвращает `unknown` без модели — замеряется скорость привязки,
а не качество разбора. Серверные времена отдельных запросов — миллисекунды;
полный обход упирается в число HTTP-запросов, а не в разбор.

## Память

- Baseline (пустой стор): ~8 МБ RSS.
- Пик после импорта 97 МБ: **~873 МБ RSS (~9× от файла)**, дальше
  не растёт (сессии/сообщения/проверка — без прироста).
- Причина: файл целиком в памяти + копии полезных нагрузок на пакет,
  сессию и поток + JSON-персист 251k сообщений. Оптимизация
  (стриминговый ingest, zero-copy срезы) — известное продолжение, не блокер:
  предел 200 МиБ держит пик около 1.8 ГБ, в лимит стенда 8 ГиБ влезает.

## Защитные пределы (диагностируются явно, без скрытого обрезания)

| Предел | Значение | Ответ |
|---|---|---|
| Размер записи (бэк, `MAX_CAPTURE_BYTES`) | 200 МиБ | `413 Capture too large` |
| Размер записи (фронт, до отправки) | 200 МиБ | понятная ошибка в UI |
| Журнал действий | 5 МиБ, UTF-8, 8 обязательных колонок | `400`, битые строки считаются в `skipped` |
| `POST /verify/corpus` | ≤ 8 файлов | `400 too many files` |
| Дефолтный лимит тела Axum (2 МиБ) | отключён | иначе рвал бы импорт до наших проверок |

## Дефекты, найденные этим прогоном (исправлены)

1. **Молчаливое обрезание файлов > ~64 КиБ.** Цикл чтения pcap трактовал
   `Incomplete` (пакет не влез в 64-КиБ окно `pcap-parser`) как конец файла:
   от записи оставались первые ~166 пакетов безо всякой диагностики.
   Исправление: `core/src/pcap/reader.rs` — `refill()` + повтор, в конце —
   счётчик `truncated`. Прямое нарушение «без скрытого обрезания данных».
2. **Дефолтный лимит тела Axum 2 МиБ** рвал импорт больших записей обрывом
   соединения. Отключён в `main.rs`, действует свой предел 200 МиБ.

## Как повторить

```bash
python3 scripts/perf/gen_load.py /tmp/load.pcap
cargo build --release -p protocol-lab-api
./target/release/protocol-lab-api --port 18095 --data-dir /tmp/pl-perf &
echo $! > /tmp/pid
PERF_PORT=18095 PERF_PIDFILE=/tmp/pid PERF_PCAP=/tmp/load.pcap \
  PERF_TMPDIR=/tmp python3 scripts/perf/measure.py
```
